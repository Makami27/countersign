# DECISIONS

## D1: Build Countersign
Context: 11+ candidates checked (IDEA_CHECK*.md, STAKEHOLDERS.md).
Decision: Countersign, Track 2 Smart Agents for Real Life; also aims at Best Walrus Memory.
Rejected: Forward, because the forward window before 10 Nov is too short for honest results; Closebook, because Sui transfers have no memo, so matching is ambiguous; storage expiry watchdog, because Walrus Console now auto-renews.
Consequence: all briefing work now targets Countersign.
Where: briefing/IDEA_CHECK_FINAL.md
Date: 2026-10-30 (team decision)

## D2: Walrus Memory is the source of truth; the local DB is a rebuildable index
Context: we need transactions and UNIQUE constraints (nonces, digests), but the event's deletion test needs Walrus Memory to be essential.
Decision: every payee version, change request, verdict and receipt is written to Walrus Memory as an **agent-signed** record. SQLite holds an index rebuilt from Walrus Memory (`listMemories` + recall) on start.
Rejected: DB as source of truth (memory becomes decorative); memory only, no DB (no atomic nonce or digest uniqueness).
Consequence: a "wipe the DB, restore from Walrus, same state" test is part of the gate.

## D3: Memory records are signed by the agent's own key
Context: poisoning can arrive as text shaped like a record (K8), or through any writer with relayer access.
Decision: each record carries an ed25519 signature by the Countersign agent key over its canonical JSON. Unsigned or badly signed recalls are dropped and counted.
Consequence: "the memory said so" is never enough; "*we* wrote it and signed it" is.

## D4: Proof of control is never proof of identity
Context: an attacker can sign for, or round-trip from, their own address.
Decision: a change needs **continuity** (signature from the current verified address) **or** owner confirmation out of band plus a cooldown, **plus** proof of control of the new address.
Where: PRD §6.

## D5: Defaults pending team confirmation
TypeScript/Node 24, MemWal SDK (TS), `@mysten/sui` v2, Gemini for extraction, Telegram channel, SQLite, Vercel or Railway for hosting. Change by adding a D-entry.

## D6: One Walrus Memory namespace per payee + a completeness check
Context: feasibility F3. `listMemories` is metadata only; `recall` is top-K (≤100) similarity search, so there's no "fetch all".
Decision: namespace `countersign:<owner>:payee:<id>`; rebuild via `recall({ topK: 100 })` with no `maxDistance`; require recalled count == listed count and `dropped_count == 0`, else `MEMORY_INCOMPLETE` (blocks payment). Cap at 100 records per payee; past that, roll over to a new namespace with a signed pointer.
Rejected: one big namespace (incompleteness undetectable); trusting the local DB (breaks D2).
Consequence: spike S12 is load-bearing.

## D10: Extraction model and who converts amounts
Context: G1–G3 in REALITY_SPIKES. The model put a decimal into a base-units field; a pinned model name was answered by a newer version; newer Flash models returned 503 on the free tier.
Decision: `GEMINI_MODEL=gemini-3.5-flash`. The model returns `amountText` exactly as written; `usdcToBaseUnits` in code converts it (6 decimals, strict pattern, > 0) and the number must stand alone in the message, so "10" can't become "1". Model output is parsed with a zod `.strict()` schema: an unexpected field (e.g. `status`) refuses the whole output as no proposal, where before it was dropped silently. An outage, 429, 503 or empty answer is `UNKNOWN`: nothing changes and the owner is told to resend. Every READ result carries the `modelVersion` that answered.
Rejected: asking the model for base units (G1); dropping unknown fields (a model that tries to set a status should not have its other fields trusted); the `-latest` aliases (not reproducible).
Where: `packages/adapters/src/gemini/{proposal,extract}.ts`, tests X01–X06

## D11: Payment intents are digest-first, kept in SQLite, and settle by digest only
Context: V07 and FAILURE_MODES ("persist intent before effects", "UNKNOWN has no resubmit edge"). The SDK can build and sign a transaction locally, which fixes its digest before anything is sent, and address-balance gas gives every transaction a validity window that ends at the next epoch (P1).
Decision: the engine reserves the day's budget and inserts a RESERVED intent in one transaction (`PaymentLedger.reservePayment`). The runner builds and signs locally, stores the digest and last valid epoch while moving to SENDING (a CHECK forbids SENDING without a digest; digests are UNIQUE), then submits once. A thrown submit is UNKNOWN. SENT and UNKNOWN are reconciled only by looking the digest up through Tatum: found with the exact USDC credit → SETTLED; found and failed → FAILED; not found → FAILED only after the validity window has passed and never from SENT. A payment found still SENDING at startup is moved to UNKNOWN first. FAILED gives the reservation back. A SQLite trigger generated from `PAYMENT_TRANSITIONS` rejects any other state move, even from raw SQL. Malformed or zero amounts are `AMOUNT_INVALID` (new reason code); a payee with records but no verified version is `PAYEE_NOT_VERIFIED`, one with no records `UNKNOWN_PAYEE`.
Intents live in SQLite only (on the persistent volume), not in Walrus Memory: a 20 s memory write before every send would double payment latency, and the intent row is an operational ledger like nonces (D2). The final outcome is written to Walrus Memory as an agent-signed receipt (pending the types.ts change).
Rejected: resubmitting on timeout (double payment); writing intents to memory before sending (latency, and a timed-out memory write would block the payment for no safety gain); a SENDING → SETTLED edge (the PRD machine stays as written; interrupted sends go through UNKNOWN).
Where: `packages/core/src/payments.ts`, `packages/adapters/src/sqlite/paymentLedger.ts`, `packages/adapters/src/tatum/payments.ts`, `packages/adapters/src/payments/runner.ts`

## D12: One receipt type for every final outcome
Context: V14 needs a receipt page for every outcome; the owner approved one general receipt (2026-10-30).
Decision: `ReceiptRecord` replaces `RefusalRecord`. Verdicts PAID, PAYMENT_FAILED, REFUSED, CHANGE_VERIFIED, CHANGE_REJECTED; a closed `reason` code (no free text); ordered `checks` from `CHECK_CODES` (OWNER_CONFIRMED and COOLDOWN_ELAPSED cover the owner path); `memoryBlobIds` naming the payee version a payment used or a change created; `suiDigest`; `network`. Receipts are written only for final outcomes; UNKNOWN payments stay in the ledger until reconciled. They live in `countersign:<owner>:receipts` (replacing `:refusals`). Known-attack matching reads REFUSED/CHANGE_REJECTED receipts whose reason is not retryable. Old `refusal` records are skipped on restore and counted as `legacy`, not as forgeries. V13: an expired request is EXPIRED, a reused one NONCE_REUSED, and a signature from the wrong wallet WRONG_WALLET (the verifier asks Tatum again without the address; if the signature is valid for someone else it is WRONG_SIGNER). Memory reads now return blob ids (`StoredText`). A payment receipt id is derived from the payment id so a retried write is identical.
Where: `packages/core/src/{types,vocabulary,receipts,engine,memoryBook}.ts`, `adapters/src/sqlite/indexStore.ts`, tests in `packages/core/test/receipts.test.ts`

## D13: Payee signatures are verified once, at the time of the change
Context: S10z. A zkLogin signature stops verifying after its maxEpoch (the owner's was 1298), so re-checking it later would turn a valid history into INVALID.
Decision: the change is verified through Tatum when it happens. The agent-signed VERIFIED record stores, per signature, its role, signer, scheme (ED25519 / ZKLOGIN), maxEpoch and the epoch it was checked at. Restore trusts the agent's signature on that record and never re-verifies payee signatures; payment never consults the verifier. Any public "verify it yourself" view must say that zkLogin signatures stop verifying after maxEpoch and show the epoch it was checked at, instead of showing a later re-check as INVALID.
Test: "D13 a zkLogin-verified payee stays payable after the signature's maxEpoch, including after a restore" in `packages/core/test/receipts.test.ts`.

## D14: A payee is payable only after its own wallet signs (V03)
Context: owner-approved types.ts change (2026-10-31): 1 + 2 + 3 + 4.
Decision: adding a payee writes a STATED record (`onboarding_requested`, nonce, 24 h expiry) and a pending onboarding; it is listed as "Waiting for the payee's wallet" and can never be paid. The payee's wallet signs "Countersign payee onboarding v1" (payee, name, address, nonce, expiry); after Tatum verifies it, a VERIFIED `payee_onboarding` record stores the control proof and its verification details (D13). The display name lives on every `PayeeVersionRecord` (`name`). Adding a payee runs the known-attack and look-alike checks against all verified addresses, and again at completion. The old `owner_onboarding` kind is gone: agent-signed records of that kind (lab, Act 1 demo payee) are skipped as legacy and are never payable; the Act 1 demo payee is re-onboarded through the signing page later. Pending onboardings are their own type (`PendingOnboarding`), so `PendingChange.fromAddress` stays required. A record's signature is checked before it is classed as legacy, so an unsigned record can never pass as legacy (C10 caught the wrong order). The lab seeds its payees through the same request-and-sign path with sandbox keys. New reason `NAME_INVALID`.
Where: `packages/core/src/{onboarding,engineWrites,records}.ts`, `packages/core/test/onboarding.test.ts`

## D16: One process for the agent, the bot and the web app
Context: the owner app needs the same engine, ledger and payment runner as the Telegram bot; two processes would each rebuild the index from memory and race on payments.
Decision: `apps/agent/src/main.ts` starts the engine, the payment runner (plus a 60 s reconcile loop for SENT/UNKNOWN payments), the Telegram bot and the web server (`startWebServer` with an owner context) in one Node process over one SQLite file. `apps/web/src/main.ts` remains a public-only server (landing, lab, proof) for local design work. Owner sign-in: the bot's /login issues a 10-character code from a 32-letter alphabet (hash stored, 10 min, single use); redeeming it sets an HttpOnly, Secure, SameSite=Strict session cookie; owner writes also need an `x-countersign: 1` header (CSRF), and logins and writes are rate-limited per client. Caps and the cooldown are owner settings in SQLite, read live by the engine. Payments are previewed (all checks, nothing reserved) before the owner confirms with a button, in Telegram and on the web; the web pay request also carries the address the owner saw and is refused if the head changed. A failed restore no longer stops the process: payments are refused by the memory checks until memory reads completely (V18).
Where: `apps/agent/src/{main,telegram,telegramText}.ts`, `apps/web/src/{server,http,labRoutes,ownerRoutes,ownerViews,ownerAuth,ownerSettings,ownerContext}.ts`

## D19: Render free + Neon Postgres (supersedes D15, D17 and D18)
Context: team decision (2026-10-31). Render's free instance sleeps after about 15 minutes without inbound traffic, restarts at times, and its disk is wiped, so nothing may depend on local files.
Decision: one free Render Docker web service (region Ohio, next to Neon's us-east-2) runs the same single process (D16), kept awake by an external 5-minute ping to `/api/health`. With `DATABASE_URL` set, the payee index, payment ledger, Tatum rate gate, owner sign-in codes and sessions, settings and change steps live in Neon Postgres over the direct (non-pooled) endpoint with TLS verify-full; without it they stay in SQLite, which unit tests and local runs keep using. Walrus Memory stays the source of truth (D2): every boot rebuilds the index from it and resumes reconciliation from the ledger in Postgres.
Guarantees kept: the `IndexStore` and `PaymentLedger` ports are now async; the reservation is one transaction that locks the day's budget row (`SELECT … FOR UPDATE`), re-reads the payee's verified head and refuses with `PAYEE_CHANGED` unless the intent pays that head; the engine also serialises work per payee. CHECK constraints, the allowed-transition trigger and the unique digest before SENDING exist in both schemas. A database error or timeout is an error, never a reservation or a move; Telegram replies "Nothing was decided". No session-level advisory locks.
Free-tier care: the reconcile and change-completion loops skip the database while nothing is open, so Neon's compute can suspend; SIGTERM stops Telegram polling first so a redeploy never leaves two pollers.
Where: `packages/core/src/{ports,engine,keyedMutex}.ts`, `packages/adapters/src/{postgres,sql}/*`, `packages/adapters/src/sqlite/*`, `apps/agent/src/{storage,main,config}.ts`, `apps/web/src/{ownerAuth,ownerSettings,changeSteps,proof}.ts`; tests `packages/adapters/test/support/ledgerContract.ts` (run on SQLite in `pnpm test` and on a throwaway Neon schema in `pnpm test:live`), `packages/core/test/races.test.ts`.
Rejected: a synchronous Postgres bridge (a worker thread blocking the event loop on every query); keeping Fly (team decision).

## D20: Owner wallet signs sensitive actions (V20)
Context: a stolen Telegram account could sign in to the owner app with /login and add payees, confirm address changes or raise caps.
Decision: the owner registers a Sui wallet once (it signs a registration message; Tatum verifies it). Every sensitive action is answered with HTTP 428 and the exact approval message (action, its fields, a one-use nonce, a 10-minute expiry); the browser signs it with the owner wallet and resends; the server checks every required signature through Tatum before consuming any nonce. The owner wallet is an agent-signed `owner_wallet` record in Walrus Memory (`countersign:<owner>:owner`), cached in Postgres and restored on boot; if memory can't be read and the cache is empty, sensitive actions are blocked rather than letting someone register a new wallet. Replacing it needs the old wallet's signature, or a 72 h wait with Telegram notices that the old wallet can cancel. Loosening limits (higher caps or a shorter cooldown) needs a signature; tightening them doesn't. Every sensitive action sends a Telegram notice.
Where: `apps/web/src/{ownerApprovals,ownerGate,ownerWallet,ownerWalletRoutes}.ts`, `apps/web/client/{approvals,views/ownerWallet}.ts`, `packages/core/src/types.ts` (`OwnerWalletRecord`), `THREAT_MODEL.md`; tests `apps/web/test/ownerWallet.test.ts`.
Rejected: a Telegram code as the second factor (the attacker has Telegram); keeping the owner wallet only in Postgres (a wiped database would reopen first-run registration).

## D21: Scheduled payments (V21)
Context: rent and subscriptions repeat; the owner wants them paid without asking each time, without giving a schedule any way around the checks.
Decision: a schedule is an agent-signed `schedule` record in Walrus Memory (`countersign:<owner>:schedules`): payee, amount, weekly, every two weeks, monthly or yearly, a weekday (1 Monday to 7 Sunday) or a day of the month 1–28 (UTC), with the owner-wallet approval that created, changed or deleted it (V20 kinds `create_schedule`, `change_schedule`, `delete_schedule`). Postgres caches the sealed records; the cache is opened with the agent key, so an edited row is ignored. Each run re-reads the schedule from Walrus Memory, then makes a normal payment: payee memory complete, verified head at run time, per-payment and daily caps, receipt. The key `schedule:<id>:<period>` is the receipt's `ref` and, as `pay_schedule_<id>_<period>`, the payment's primary key, so a period can be reserved once across ticks, agents and restarts. A RESERVED run found after a restart is sent only after re-checking the payee's head; if it changed, the run fails with nothing sent. Retryable refusals (MEMORY_INCOMPLETE, PAYEE_CHANGED) retry hourly within the period with one Telegram notice; other refusals (CAP_EXCEEDED, no verified payee) close the period. If the agent was down, only the latest due period runs, once, and its notice says it ran late and names the earlier periods that were not paid. UNKNOWN (Tatum submission) stays UNKNOWN and is never resent. Every run ends in a Telegram notice with the receipt link.
Where: `packages/core/src/{schedule,scheduledPayments,paymentChecks}.ts`, `packages/core/src/types.ts` (`ScheduleRecord`), `apps/web/src/{schedules,scheduleRuns,scheduleRoutes}.ts`, `apps/web/client/views/schedules.ts`; tests `apps/web/test/{scheduleRuns,scheduleRoutes}.test.ts`.
Periods are calendar-fixed so editing a schedule can never add a run: weekly = ISO week (`2026-W45`), two weeks = fixed pairs of weeks counted from Monday 5 Jan 1970 (`2026-11-09-2w`, the pair's Monday), monthly = `YYYY-MM`, yearly = `YYYY`.
Rejected: paying every missed period on boot (a long outage would send several payments at once, unseen); retrying a FAILED run in the same period (one payment per period is the guarantee); a cron outside the process (Render free has none, and a second process would be a second poller).

## D22: Shared scam memory and the hidden blacklist (V22)
Context: an attacker who fails against one owner tries the same address on others; agents can warn each other without revealing who was targeted.
Decision: a LOOKALIKE_ADDRESS or KNOWN_ATTACK_PATTERN refusal writes an `attack_seen` record to `countersign:shared:attacks`: attacker address, reason, receipt id, the reporting agent's public record key (`agentKey`) and time, signed with that key; nothing about the payee, owner or verified address. Each agent rebuilds an in-process blacklist from the namespace at boot and every 10 minutes, keeping only records whose signature verifies against their own `agentKey` (zod `.strict()` shape check first), younger than 90 days, not retracted by the same key, and not from its own key. A match refuses with SEEN_BY_OTHER_AGENT; the receipt names the first other agent's receipt and the number of distinct agent keys. Rules: it never blocks an address that is VERIFIED here, and payments never consult it; a change requested from a message is refused, but one the owner requests in the app can still complete when the payee's current wallet signs (continuity overrides the flag), never on the owner-confirmed path; onboarding a flagged address is refused; SEEN_BY_OTHER_AGENT refusals are not re-shared and don't become local attack memory, so one report can't amplify itself. A retraction is an `attack_retracted` record signed by the reporting agent, written only with the owner wallet's signature (V20 kind `retract_shared_report`). Unreadable shared memory means local checks only. The blacklist has no list method and no endpoint.
Limits: Walrus Memory isolates namespaces per account, so agents share only if they write to the same account (distinct delegate keys). Distinct agent keys are cheap, so a count is evidence, not proof; that's why a flag can't touch a VERIFIED payee and continuity overrides it. The 100-record read cap means a larger shared namespace reads as incomplete, i.e. local checks only.
Where: `packages/core/src/{sharedAttacks,sharedFlags,engineWrites,onboarding,engine}.ts` (the list is `@countersign/core/shared`, so zod stays out of the browser bundle), `packages/core/src/{types,ports,vocabulary}.ts`, `packages/adapters/src/signer.ts`, `apps/web/src/sharedReportRoutes.ts`, `apps/agent/src/main.ts`; tests `packages/core/test/sharedAttacks.test.ts`, `apps/web/test/sharedReports.test.ts`.
Rejected: a threshold of several agents before refusing (one honest report should protect the next owner, and the overrides cover false flags); publishing the blacklist (it would hand attackers a list of burned addresses to avoid and victims' timelines).

## D23: Only attack refusals become attack memory (fix before deploy)
Context: any non-retryable refusal with an address (for example CAP_EXCEEDED, which names the payee's verified address) was stored as known-attack memory, so a later message containing that payee's address would be refused as KNOWN_ATTACK_PATTERN and shared.
Decision: known-attack memory comes only from LOOKALIKE_ADDRESS, KNOWN_ATTACK_PATTERN and SEEN_BY_OTHER_AGENT refusals, and from a change rejected for SIGNATURE_INVALID on the unproven new address. Payment refusals and other change rejections (EXPIRED, NONCE_REUSED, WRONG_WALLET, NO_CONTINUITY, COOLDOWN_ACTIVE, CONTROL_NOT_PROVEN) never are. A VERIFIED payee's current address never matches, whatever is on record. A repeat of a second-hand flag is refused as SEEN_BY_OTHER_AGENT, never KNOWN_ATTACK_PATTERN, so it is not re-shared, and the owner-app path that a continuity signature can override stays open. The rule is applied when a receipt is indexed, and every boot rebuilds the index from Walrus Memory, so receipts indexed under the old rule stop matching on the next restore.
Where: `packages/core/src/{receipts,knownAttacks,engine,onboarding}.ts`, `apps/agent/src/screen.ts`; tests `packages/core/test/attackMemory.test.ts`.

## D26: Groq first, Gemini as fallback, plain commands by code (team decision: everything free)
Context: Gemini's free tier allows 20 requests a day per model (`GenerateRequestsPerDayPerProjectPerModel-FreeTier`, seen 1 Nov); the measurement used it up and blocked the live agent. No billing (team decision).
Decision: plain pay commands for a known payee ("pay landlord 0.10", "send 2.5 USDC to designer"), and any message with a look-alike or known-attack address, are read by code with no model call. Everything else goes to Groq (`openai/gpt-oss-120b`, free tier 1,000 requests/day and 8,000 tokens/minute per model, read from its rate-limit headers), and to Gemini only if Groq gives no answer. Both answers go through the same strict check (`toProposal`); Groq's habits of `null` fields and "2.50 USDC" are normalised before it, and the amount must still stand in the message as written. /status shows the provider, the fallback count and Groq's requests left today.
Where: `packages/adapters/src/{groq/extract,model/extraction}.ts`, `apps/agent/src/{screen,modelStats,main,config}.ts`, `apps/web/src/statusPage.ts`; tests `packages/adapters/test/groq.test.ts`, `apps/agent/test/screen.test.ts` (X08, X09).
Rejected: Gemini billing (team decision); a local model (no free host with enough memory).

## D27: Sign in with the owner wallet; login codes removed (V23)
Context: a /login code from Telegram was enough to open the owner app, so a stolen Telegram account could read everything and start sensitive actions (V20 then asked for the wallet, but the session was the attacker's).
Decision: the owner app signs in with a Sui wallet. The server issues a one-time message (`Countersign sign-in v1`, domain from PUBLIC_BASE_URL, purpose, address, nonce stored hashed, 10-minute expiry); the browser signs it with `signPersonalMessage` from a click-first button; Tatum verifies it before the nonce is consumed. Sessions (`wallet_sessions`) carry the owner id and wallet; cookie and CSRF as before. If no owner wallet is registered, the first wallet to sign in becomes it (an agent-signed `owner_wallet` record whose proof is the sign-in signature) with a Telegram notice; afterwards only that wallet can sign in, and unreadable owner memory blocks sign-in instead of letting someone else register. `login_codes` and the code box are gone; the bot's /login replies with the sign-in link. Sensitive actions still need a fresh approval signature.
Where: `apps/web/src/{ownerAuth,signInRoutes}.ts`, `apps/web/client/views/signIn.ts`, `apps/agent/src/{telegram,telegramText}.ts`; tests `apps/web/test/ownerAuth.test.ts`, `apps/web/test/support/signIn.ts`.
Rejected: Sign-In with Ethereum style multi-chain messages (Sui only here); keeping codes as a fallback (it would keep the Telegram hole open).

## D24: Up to 10 owners, isolated by Postgres schema (V24)
Context: the agent served one owner; a partner and judges need their own agents without any way to reach each other's money or records.
Decision: each owner gets a runtime built by the same code (`buildOwnerRuntime`): its own engine, index, ledger, settings, change steps, approvals, owner wallet, schedules and shared-memory view, on a Postgres pool pinned to its own schema (`owner_<id>`, `search_path` set on the connection, so its queries can't name another owner's tables). The admin owner keeps its existing data in `public` under its existing owner id; there is no migration of live tables. Global tables (owners, wallet sessions, sign-in nonces, owner keys, the Tatum rate gate) live in `public` and are reached only through the directory. A session resolves to exactly one owner; `/sign/:nonce` and `/r/:receipt` stay public and are found by looking across owners. Signing in: a registered owner wallet opens its owner; the admin address (ADMIN_WALLET) registers the admin if it has none; any other new wallet creates an owner (up to MAX_OWNERS, default and maximum 10) and registers itself as that owner's wallet; unreadable owner memory blocks sign-in. Each new owner gets an agent wallet and a record-signing key generated on the server, sealed with AES-256-GCM under MASTER_KEY (the owner id is the associated data), stored in `public.owner_keys` and backed up as ciphertext to Walrus Memory (`countersign:<owner>:keys`). Without MASTER_KEY the agent serves only the admin. Each owner's agent signs with its own key, so V22 counts owners' agents as distinct.
Telegram (V24b): the admin's chat (TELEGRAM_OWNER_USER_ID) is bound to the admin owner and can't be relinked. Other owners connect a chat from the owner app with a one-time `t.me/<bot>?start=<token>` link (16 random bytes, stored hashed, 10 minutes, one chat per owner, a new chat replaces the old). Every bot update resolves its sender to one owner and runs that owner's engine; pay confirmations remember their owner; unlinked chats get a sign-in hint and nothing is stored. Notices go to each owner's linked chat; the admin is told when an owner connects a chat.
Dashboard (V24c): the agent card links the Sui and Circle testnet faucets (no automatic grants) and shows live balances through Tatum; a checklist is computed from the owner's own records (funded, payee added, link signed, paid, scam refused, Telegram); "Check a message" sends pasted text down the forwarded-message path (channel `paste`, so the owner-app override for flagged addresses never applies), code first and the model only for free text, and a pay request is only previewed. The admin page (admin session only) lists owners with wallet, join time, payees, last activity and last-hour usage; removing one needs the admin wallet's signature and deletes their sessions, keys, Telegram link and schema. Every other owner has in-memory hourly allowances (60 Walrus writes, 200 Tatum calls, 60 model calls); past them, owner-app writes and bot messages answer "Busy … Nothing was changed". Counters live in memory so they never wake the database, and reset on restart.
Limits: whoever holds MASTER_KEY and the database (or the Walrus backup) holds every other owner's keys and agent funds; losing MASTER_KEY loses them. Removing an owner deletes its sessions and directory entry; its Walrus records can't be erased.
Where: `apps/web/src/{ownerDirectory,ownerRuntime,signInRoutes,server}.ts`, `apps/agent/src/{main,ownerKeys,storage,config}.ts`; tests `apps/web/test/crossUser.test.ts`, `apps/web/test/support/multiOwner.ts`.
Rejected: an `owner_id` column on every table (one missed filter is a leak); moving the admin's live tables into a new schema (risk to live data for no isolation gain).

## D25: Public /demo on the lab sandbox (V25)
Context: judges and visitors should see the engine decide without signing in or touching anyone's data.
Decision: /demo reuses the lab: a per-visitor sandbox agent (cookie, 30 minutes, at most 500 sessions, in-memory memory, the same rate limits) seeded with two payees whose own sandbox wallets signed. Letters are built on the server from the session's own payee addresses: a genuine payment request (paid), "my wallet changed" to a look-alike (LOOKALIKE_ADDRESS), a fake payment history (kept STATED, never payable), and a forged VERIFIED record written straight into memory (ignored on restore; the next payment still goes to the proven address); "paste your own" uses the lab's message path. Signature cards show each payee's verified address and how many stated versions memory holds; Activity lists the session's decisions with sandbox receipt ids (kept only in the sandbox, not on Walrus Memory, so they have no /r page). On phones the three areas are tabs. The landing gets "Try the demo" and "Sign in with your wallet".
Where: `apps/web/src/{lab,labLetters,labWallets,labRoutes,server}.ts`, `apps/web/public/demo.html`, `apps/web/client/demo.ts`; test `apps/web/test/demo.test.ts`.
